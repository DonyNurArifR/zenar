# R3: background compaction with a swap that reclaims memory

Status: **stage 1 and stage 2 implemented and verified (section 15).** Stage 1 is the catalog protocol (section 13). Stage 2 is the background build,
the catch-up, the short swap and the reclamation of section 3 and 4, with the deviations in section 14. The vector index is
unchanged. The measurements are from the reference machine (Apple arm64 laptop, release build), and are in
`docs/BENCHMARKS.md`. An estimate is marked as one.

Context: `COMPACTION.md` has the investigation. This document is the design, the crash analysis, the test plan and the
acceptance criteria.

## 1. What R3 does

Compaction rewrites the document log without its dead records, and rebuilds the in-memory document structures from the
rewritten log. It does this in the background, so that the collection lock is held only for a short swap at the end.

Three things are carried over from the snapshot to the new state, and nothing else:

- the **live documents** at the snapshot, which are copied as the same frames, in the same order;
- the **tail**: the bytes appended to the old log after the snapshot, which are copied verbatim;
- the **vector index**, which is not touched. Compaction changes no vector, so the vector index and its file stay as they are.

## 2. The snapshot and the tail: representation

Two numbers describe a compaction, and they are all the state it needs:

- `S`, the **snapshot length**: the length of the old log at the moment the compaction starts, counted in committed bytes.
- `W`, the **committed watermark**: the length of the old log up to the end of the last committed write. It is maintained by
  the write path. A write moves `W` forward only when it commits (after its log sync, in `commit_batch` and in the delete
  commit), never when it stages. A rollback truncates the log to a point at or after `W`, so `W` never moves back.

Why the watermark rather than the file length: a group that is in its window has staged bytes in the old log. Those bytes
are not committed and can still be rolled back. Reading them into the rewrite would copy writes that may never happen. Bytes
below `W` are final: nothing truncates below `W`, and no committed frame changes.

The background build does not need the in-memory row table. It reads the old log from the front and does what replay does:
a PUT adds a live frame, a DEL removes its id. The frames live at `S` are then the frames the rewrite writes. This is the
same computation replay performs, so the result equals the in-memory state at `S` (the replay invariant that the document
store already keeps).

The new state is a second document store, `N`, with its own row table and indexes. `N` is built by replaying the rewritten
temporary log, `T`, which holds the live frames and then the tail. It is an ordinary `DocStore`, opened on `T`.

## 3. The background build

Runs without the collection lock, except for two short reads of `W`.

1. Read `W` and `S := W` under the read lock.
2. Scan the old log from byte 0 to `S`, keeping the offset and length of each live PUT (the scan of section 3 of
   `COMPACTION.md`). Write those frames to `T` in order.
3. Open `T` as `N`, by replay. This is the replay cost of today's compaction, now off the lock (156 ms at 500,000 live rows,
   measured earlier).
4. **Catch-up**, repeated until the lag is small: read `W` (read lock); copy the old-log bytes `[p, W)` to the end of `T`
   and apply those frames to `N` (a function that replays a tail buffer with the offsets it will have in `T`); set `p := W`.
   Each round is bounded by the writes committed during the previous round, so the lag shrinks when writes are slower than
   the build.

Writes continue during all of this. They append to the old log and commit as usual. They never touch `T` or `N`.

## 4. The swap

Runs as a leader operation, under the collection lock, between write groups. Because a leader runs groups one at a time, no
group is in its window: every staged write is committed, and `W` is the end of the log.

- **S-a.** Copy the old-log bytes `[p, W)` to `T`, and apply them to `N`. This is the final tail: the writes since the last
  catch-up round.
- **S-b.** Sync `T`.
- **S-c.** Catalog write **P1** (one atomic replace): `durable_log_len := len(T)` and `compaction_pending := { old_len: L_old }`,
  where `L_old` is the length of the old log at this point. Section 5 explains why both fields are needed.
- **S-d.** Close the old log handle (Windows refuses to rename over an open file; on failure, reopen it).
- **S-e.** Rename `T` over the log path.
- **S-f.** Sync the directory.
- **S-g.** Catalog write **P4** (one atomic replace): `compaction_pending := none`.
- **S-h.** Swap: the collection's document structure becomes `N`, which already has an open handle to the file now at the log
  path (the same inode, because the rename does not change it). The old structure is dropped here, which frees its rows, its
  postings and its file handle. The old log's inode is freed by the kernel when the rename removes its last name.
- **S-i.** Release the lock.

No reopen. The rows and indexes in `N` are the ones that serve reads after the swap.

Writes resume only after S-g. So the file is not written while `compaction_pending` is set, which is what makes the
pending record decisive (section 5).

## 5. Crash consistency: the protocol and why it is needed

### What rename alone does not give us

A rename is atomic for one name. The compacted log is one object, and the catalog that records its length is another. A crash
can fall between the two. A rename also is not durable until the directory is synced, so a power loss can bring back the old
name. Three facts follow:

1. The catalog's recorded length must never exceed the length of the log file that a reopen will find. The shortened-file
   check refuses a database whose file is shorter than its recorded length, and that refusal is the guarantee that a silent
   truncation is caught. Recording the new (shorter) length after the rename would make a crash in between refuse a good
   database. So the catalog records the new length **before** the rename.
2. Recording the new length before the rename, on its own, leaves the reopen unable to tell two states apart: the old file
   still in place (after a crash, or after a power loss that undid the rename), and an external truncation of the old file to
   a length between the new length and the old one. Both have a file shorter than the old recorded length and at least the new
   length. The reopen would accept either, and the second would be a silent loss.
3. The fix is to record both lengths, **before** the rename, in one atomic catalog write: the new length (the recorded
   length) and the old length (the pending record). A reopen can then say which state it is in, exactly.

This is the protocol's only extra record. It is not a generation id. A generation id would be needed to tell two files of
the same length apart, and the design avoids that case: writes wait for P4, so the log file's length is either `len(T)`
(after the rename) or `L_old` (before it), and nothing else.

### The reopen rules

Run on open, before any file is read for replay, for each collection with a catalog entry:

| Catalog | Files on disk | Action |
|---|---|---|
| no pending record | log length `>= durable_log_len` | normal (today's check). Delete a stale `*.log.compact`. |
| no pending record | log length `< durable_log_len` | refuse (RecoveryError). Unchanged. |
| pending `{old_len}`, `durable_log_len = N` | log length `== N` | the rename happened. Clear the pending record. Delete a stale `*.log.compact`. |
| pending `{old_len}`, `durable_log_len = N` | log length `== old_len` | the rename did not happen (or was undone). Set `durable_log_len := old_len`, clear pending, delete `*.log.compact`. |
| pending `{old_len}`, `durable_log_len = N` | any other length | refuse (RecoveryError): the log was changed outside Zenar. |

Then the usual replay and reconcile run. Both candidate files replay to the same documents, so the choice of file does not
change the content.

If `N == old_len` (nothing was deleted or added), both rows match the same file and both give the same result.

### The crash-state table

Each row is a state a crash can leave, the files and catalog as they are, and what reopening does. "Committed" means
committed before the swap began. Power loss also drops unsynced data, and the rows cover that.

| # | Crash point | Old log | `T` | Catalog | Reopen result | Committed documents lost? |
|---|---|---|---|---|---|---|
| 1 | Before `T` is written | `L_old` | none | old, no pending | normal; nothing to delete | no |
| 2 | During the rewrite or a catch-up round | `L_old` | partial | old, no pending | delete partial `T`; normal | no |
| 3 | After `T` is synced, before P1 | `L_old` | complete | old, no pending | delete `T`; normal | no |
| 4 | During P1's atomic write | `L_old` | complete | old or P1 (atomic: one of the two) | if P1: rule "file == old_len" (`L_old`) applies; if old: as row 3 | no |
| 5 | After P1, before the rename | `L_old` | complete | P1 (pending) | rule "file == old_len": set `durable_log_len := L_old`, clear pending, delete `T` | no: the old log holds every committed write |
| 6 | During the rename | `L_old` or `len(T)` | the other, or none | P1 | rename is atomic for the name: the first case is row 5, the second is row 7 | no |
| 7 | After the rename, before the directory sync | `L_old` or `len(T)` (the directory may be undone on power loss) | none | P1 | rule per the file found: `L_old` as row 5; `len(T)` as row 8 | no |
| 8 | After the directory sync, before P4 | gone; the log is `len(T)` | gone | P1 | rule "file == N": clear pending | no |
| 9 | After P4, before the swap in memory | `len(T)` | gone | clean | normal replay of the new log | no |
| 10 | During the tail application or the swap in memory | `len(T)` | gone | clean | normal replay; memory is discarded | no |
| 11 | During cleanup (dropping the old structure, freeing the old inode) | `len(T)` | gone | clean | normal replay; nothing to clean on disk | no |
| 12 | After writes resumed on the new log | `len(T)` plus later writes | gone | clean | normal replay; the later writes were synced by their own commits | no: a write is lost only if its own sync had not returned, as before |
| 13 | Power loss during the tail copy (S-a) | `L_old` | partial | old, no pending | row 2 | no |
| 14 | Power loss during the sync of `T` (S-b) | `L_old` | partly synced | old, no pending | row 2 (`T` is deleted on open, unsynced data is gone anyway) | no |
| 15 | Power loss after P1 is synced, before the rename | `L_old` | synced | P1 | row 5 | no |
| 16 | Power loss after the rename, before the directory sync | `L_old` or `len(T)` | synced | P1 | row 6 or 7 | no |
| 17 | Power loss after P4 is synced, before the swap | `len(T)` | synced | clean | row 9 | no |

Rows 4 and 6 contain "one of two states" because the operation is atomic: the state after a crash is one of the two, and the
table covers both. No row leaves the collection in a state the reopen cannot classify: each combination of catalog and file
either matches a rule, or is refused.

Why committed writes are never lost: every committed write before the swap is in the old log below `W`. The rewrite and the
tail copy copy every live frame and every byte after `S`, so `T` holds every committed write too, as a live frame or as its
tombstone. Until P4 is synced, the old log is still the file a reopen can find (rows 1 to 7), and it holds all committed
writes. After P4 is synced, `T` holds them (rows 8 to 17). A write that commits after P4 is synced to the new log, by its own
sync, like any other write.

### What reopen will refuse, and why that is correct

Only the last row of the rules table refuses: a log whose length is neither the old length nor the new length, while a
pending record exists. A pending record means a swap was in progress when the process stopped. Under the protocol, the log
can only be one of two lengths then. Any other length means something outside Zenar changed the file, and refusing is the
existing rule for a file shorter than the recorded length.

### Ordering requirements, stated for the implementation

- `T` is synced before P1 (S-b before S-c). Otherwise P1 could name a length whose bytes are not on disk.
- P1 is written before the rename (S-c before S-e).
- The directory is synced after the rename (S-f), and the swap in memory happens after S-f. This matters for power loss:
  writes made on the new file are acknowledged only after it is durable, so the directory entry must be durable before any of
  them.
- P4 is written before any write resumes on the new file (S-g before S-i). Otherwise a crash could leave a pending record next
  to a log that has grown past `len(T)`, which the table above does not cover.

### Catalog format

The pending record is a new optional field of the collection entry, with a serde default. A catalog written without it still
reads, and the field's absence means no pending record. The catalog version stays 3. A version-3 reader that does not know the
field would ignore it, and that is unsafe only for a pending record, which exists only during a swap. So a database written by
this build must not be opened by an older build while a swap is pending. Reopening with this build clears any pending record.
This is a compatibility note for the changelog, not a format break for existing databases.

## 6. Failure at every stage

| Stage | Failure | Effect on disk | Effect in memory | Required action | Usable afterwards |
|---|---|---|---|---|---|
| Background build (step 2 to 4) | I/O error or allocation failure | partial `T` | `N` discarded | delete `T`; end the compaction | yes |
| S-a tail copy | I/O error | partial `T` | `N` not yet swapped | delete `T` | yes |
| S-b sync of `T` | I/O error | `T` unsynced | none | delete `T` | yes |
| S-c P1 write | error returned | catalog unchanged (atomic replace) or changed (if the error came after the rename of the catalog file) | in-memory catalog reverts | delete `T`; if the catalog on disk may hold P1, re-write the old catalog (P0). If that fails, the pending record stays; reopen resolves it by the table | yes, if P0 succeeds. If not, the next reopen resolves P1 |
| S-d close old handle | error | none | none | reopen the old handle; delete `T` | yes |
| S-e rename | error | the rename did not happen | none | reopen the old handle; delete `T`; write P0 | yes, if P0 succeeds |
| S-f directory sync | error | the rename may or may not be durable | the file is `T` and the process holds the old handle, closed in S-d | **poison**. Writing to the old handle would lose the write, and reopening resolves it by the table | no; reopen is required |
| S-g P4 write | error | P1 stays on disk | the file is `T` | **poison** (writes must not resume without P4). Reopen resolves it: the log is `len(T)` | no; reopen is required |
| S-h swap in memory | cannot fail (no I/O) | none | none | none | yes |

"P0" is the catalog write of the old `durable_log_len` with no pending record. Writing it restores the state before S-c. It
is needed on the failure paths before the rename, so that a later reopen does not see a pending record for a swap that
never happened. If P0 itself fails, the pending record is left, and the next reopen resolves it by the table. The collection
stays usable in that case, because the old log and the in-memory state still agree.

Why a rename failure does not poison, and a directory-sync failure does: a failed rename leaves the old file in place with
the old handle still valid. A failed directory sync leaves a renamed file the process has no handle to, so the process cannot
trust either side. That is the case where the existing rule (poison, reopen to recover) applies.

## 7. Concurrent inserts and deletes

- **Snapshot.** `S` and `W` are read under the read lock. Nothing else is copied.
- **Inserts** commit to the old log, below and above `S`. Those above `S` are in the tail. Their vectors are in the vector index,
  which is unchanged, so the vector index and the new `N` agree on them, once the tail is applied.
- **Deletes** remove the vector from the index at once (as now), and write a tombstone. The tombstone is in the tail when it
  is after `S`. A row that was live at `S` is in `T`, and its tombstone is applied to `N`, so `N` drops it.
- **Searches** during the build use the old structure and see the same results as before. After the swap they use `N`, which
  holds the same live documents. Deleted vectors are not in the index either way.
- **Writes during the swap** wait for the lock. The swap holds it for S-a to S-h.
- **Readers cannot keep the old structure.** A reader holds the read lock for the whole of a search, and the swap needs the
  write lock. So no reader can hold the old structure past the swap, and the old structure is dropped under the lock, when
  the last reader that could see it has finished.

The model in `tests/test_compaction_model.py` checks the logical claim: after each swap, the live documents of the new log
equal those of the old log. The Rust tests (section 8) check the same claim on the implementation, including the tail
application.

## 8. Rust test plan

The implementation is not accepted until these tests exist and pass. Each failure-injection test must be shown to fail on a
version of the swap with that step removed or reordered (a mutation check), so that the tests test something.

Hooks (test-only, `cfg(test)`, in the style of the existing window hooks): a hook at each stage S-a to S-h and in the
background build; a failure flag per stage; a window hook that pauses the build between catch-up rounds; a copy hook that
copies the directory at a named stage, for the crash tests.

**Deterministic concurrency**
1. `build_pauses_do_not_block_readers`: pause the build; searches and gets complete with the usual results.
2. `writes_during_the_build_are_in_the_tail`: pause after the snapshot; add and delete; release; after the swap the documents
   and counts equal the reference.
3. `swap_waits_for_an_in_flight_group`: a group in its window; the swap, a leader operation, must not run until it commits.

**Insert/delete interleavings**
4. `reference_model_with_background_compaction`: random adds, deletes, searches, compactions (background, at random points,
   with writes in the window), reopens; the live documents and their values match a reference after every swap and reopen.
5. `delete_of_a_row_live_at_the_snapshot`: deleted during the build; after the swap it is absent; the reopen agrees.
6. `re_added_id_across_the_swap`: deleted and added again across the swap; the live copy is the new one.

**Snapshot consistency**
7. `snapshot_excludes_staged_bytes`: a group staged but not committed at `S`; its bytes are not copied; after rollback the
   rewrite is unaffected.
8. `watermark_only_moves_at_commit`: `W` advances at each commit and not at staging or rollback.

**Tail replay**
9. `tail_replay_equals_full_replay`: for random tails, applying the tail to `N` in catch-up rounds equals replaying the whole
   new log from scratch (same rows, postings and counts).
10. `catch_up_rounds_cover_every_byte`: `p` advances to `W` each round, and no byte is copied twice or skipped.

**Failure injection at every persistence transition** (one test per stage in section 6)
11. `failed_stage_leaves_usable_collection`: failures at build, S-a, S-b, S-d, S-e: the collection is usable, the results and the
    files equal those before the compaction, and no `T` remains after reopen.
12. `failed_catalog_write_before_rename`: S-c fails: usable; the next reopen and the in-memory catalog agree.
13. `failed_directory_sync_poisons`: S-f fails: every operation returns `PersistenceError`; reopen returns the committed data.
14. `failed_p4_poisons`: S-g fails: poisoned; reopen resolves to the new log.

**Crash recovery with copied directories**
15. For each row of the crash-state table: copy the directory at that point (the copy hook), reopen the copy, compare the
    documents with the reference. Rows 1 to 17, one test each, named after the row.
16. `pending_record_with_old_length_is_reverted`, `pending_record_with_new_length_is_completed`, `pending_record_with_other_length_is_refused`:
    the three reopen rules, each with a hand-built catalog and log.
17. `stale_temporary_log_is_removed_on_open`.

**Poisoning**
18. Every poisoned state refuses every operation (reads included) until reopen, and a reopen after a poisoned swap returns the
    committed documents.

**Repeated compaction and memory**
19. `repeated_compaction_memory_is_bounded`: 20 rounds of the sliding window; the heap in use after each compaction stays within
    a fixed band (the counting allocator from `compaction_bench`). The test fails if the heap grows with the number of rounds.
20. `reclaimed_rows_are_gone_from_memory`: after a swap, the rows and postings hold only live documents (checked through the
    row count and the index sizes, not through the log).
21. `old_structure_is_dropped_at_the_swap`: the old structure's drop is observed (a drop counter in the test build) before the
    lock is released.

**Search correctness and top_k during compaction**
22. `search_top_k_during_build_and_swap`: the same top-k results (ids and scores) before, during and after a compaction, with
    writes in the window; top_k below and above the live count.
23. `filtered_search_during_swap_is_consistent`: filtered results match the reference across the swap.

**Regression tests for existing persistence guarantees**
24. The existing recovery tests (`torn_*`, `corruption_*`, `missing_*`, `log_cut_short_*`, `damaged_synced_record_*`,
    `crash_during_delete_*`, `group_*`, `failed_*`) must pass unchanged.
25. The Python kill -9 tests (`tests/test_robustness.py`) must pass.
26. The compaction model (`tests/test_compaction_model.py`) must pass.

## 9. Benchmarks: baseline, acceptance criteria, and what is measured

### Baseline (measured, current reopen-based compaction)

`compaction_bench`: 200,000 live documents, dimension 64, sliding window of +20,000 / −20,000 per round, 8 readers, 40 rounds,
3 compactions. Reference machine.

| Measure | Baseline (measured) |
|---|---|
| Delete batch that compacts (lock held, includes compaction) | 86 to 100 ms |
| Delete batch that does not compact, p50 | 22 ms |
| Searches that started during a compacting batch: p50 / p95 / p99 | 0.28 / 74 / 79 ms (n = 365) |
| Searches, all: p50 / p95 / p99 | 0.32 / 12.8 / 15.0 ms (the writer's 1,000-row batches cause the p95 and p99) |
| Writer batch (1,000 rows): p50 / p95 | 16.2 / 19.7 ms |
| Heap in use, steady, before a compaction | 51 to 53 MB |
| Heap in use, after a compaction | 35 to 37.5 MB |
| Dead-row memory reclaimed by one compaction | about 16 MB, which is about 80 bytes per dead row at 200,000 dead rows |
| Peak heap during a compacting batch | 73.6 to 75.2 MB (transient +22 MB, from the reopen replay) |

Peak heap for the whole run is 56.5 MB, measured from the seeding; the per-compaction peak above is the figure to compare.

The memory figure for a heap that grows without compaction is in `COMPACTION.md`: about 105 bytes per dead row in the document
store, and linear growth with the number of deletes.

### Acceptance criteria for R3

Each criterion is a measurement on the reference machine, with the same workload, and each is compared with the baseline
above. The swap's hold and the reader tail are the primary criteria. Estimates are not criteria.

| Measure | Criterion |
|---|---|
| Swap lock hold (S-a to S-i), from `WriteStats`, at 1,000,000 live rows | at most 40 ms, and at most 2× the swap's hold at 200,000 live rows (it should not grow with the live size) |
| Reader p99 for searches that start during a compaction | at most 2× the steady p99 of the same run, and at most 20 ms at 200,000 live rows, against 79 ms now |

| Peak heap during a compaction | at most 1.5× the steady heap, measured against the baseline's +22 MB at 200,000 live |
| Heap after a compaction | within 5% of the heap a fresh process holds for the same live documents (measured by reopening, once, in a separate run) |
| Reopen time (replay of the log) | no regression against 151 to 159 ms at 500,000 live rows |
| Repeated compaction, 20 rounds | the heap after each compaction stays within 5% of the first one |
| Compaction wall time (background build plus swap) | reported, not a criterion |
| Ordinary delete path (no compaction) | no regression against p50 22 ms in `compaction_bench` and the `write_cost` deletes |

### Measurements to make

- Each criterion above, on the implementation, with the same benchmark (`compaction_bench`, extended with a 1,000,000-row run).
- The swap's hold from the `WriteStats` counters, which already time each exclusive hold.
- Heap at each stage, with the counting allocator.

Estimates, separate from the above, and not accepted: the swap's hold of 25 to 35 ms in the earlier design (withdrawn) and the

## 10. Open issues and risks

- **Transient memory.** The build holds the old structure and `N` at once. The peak is the old structure plus a new one of
  live size. The baseline's transient is 22 MB at 200,000 live. R3's peak is expected to be similar, and must be measured.
- **The vector index does not shrink.** TurboVec keeps the capacity freed by removals (`vector_memory_probe`). Compaction
  does not change that, and the reuse of freed capacity keeps it bounded by the peak. This is not dead-row memory, but it is
  not reclaimed either. It needs a separate decision.
- **Windows.** The rename needs the old handle closed (S-d). The swap's failure paths must reopen the old handle, and the
  file-locking behaviour is not tested on Windows.
- **Compaction policy.** The trigger (dead rows above live rows and 4096) is unchanged. A policy that compacts in the
  background more often, to keep the peak down, is a separate decision.
- **Catalog compatibility.** An older build that opens a database while a swap is pending would not know the pending record.
  This is a changelog note, not a data risk, because the pending record exists only during a swap.
- **Process crash during the build** leaves a stale `T`, which is removed on open. Its disk space is reclaimed then.

## 11. Decisions needed

1. Approve R3 as the design: background build, catch-up rounds, a swap that records both lengths in P1 and clears the pending
   record in P4, and a swap that does not reopen.
2. Approve the pending record as the one addition to the catalog (section 5), with the compatibility note in section 10.
3. Approve the acceptance criteria in section 9, including the 40 ms swap bound at a million rows, as targets to measure against.

## 12. Stage 1: what is implemented and verified

The catalog protocol is implemented in the existing synchronous compaction, which still reopens the log to rebuild memory.
Background construction is not.

- **Catalog.** `Entry.compaction_pending: Option<u64>` (the old log length), serialized only when set. A catalog without the
  field reads and writes as before. The version stays 3. A failed catalog write reports `NotApplied` when the file still
  holds the old catalog (the in-memory entry reverts), and `MaybeApplied` when the rename happened and the directory sync
  failed (the in-memory entry keeps the new value).
- **The compaction** (`Collection::compact_locked`) runs the transitions of section 4: temporary log written and synced;
  pending record written (new length, old length); rename; directory sync; reopen by replay; record the lengths, which clears
  the pending record. Any failure poisons the collection.
- **Reopen** (`database.rs`, `settle_compaction`) removes a stale temporary log, then applies the rules of section 5. A
  pending record whose log is neither length refuses to open, and the log is not changed.
- **Temporary catalog file** left by an interrupted write is removed on open.

### Crash-state table, mapped to the tests

The table has 17 rows. The synchronous compaction has no tail, so rows 13 and 14 (power loss during the tail copy and its
sync) do not occur in it. Rows 4, 6, 7, 8 and 10 were verified by copies taken at the named transitions of
`compact_locked`. The rename is atomic, so "during the rename" is never a distinct directory state: the copies before and
after it cover both outcomes.

| Row | Verified by |
|---|---|
| 1, 2, 3 (before the temporary log is complete) | `crash_at_every_compaction_transition_reopens_to_the_committed_documents`, copy "before temp log" and "temp log synced" (the temporary log is removed on open) |

## 14. Stage 2: the background build and the short swap

The build runs on its own thread without the collection lock. It snapshots the committed length, writes the live frames
below it to a temporary log, replays that log into a new row table, and then catches up on the frames written since, in
rounds of up to 64 KiB. The swap is queued as a write. Under the lock it copies the last tail, syncs the temporary log,
records the pending lengths in the catalog, renames the log, syncs the directory, and swaps in the new row table. The old
row table is dropped after the lock is released. A failed build removes its temporary log. A failed swap before the
rename undoes itself and leaves the collection usable. A failure after the rename poisons it, and a reopen settles it by
section 5.

The vector index is not touched. Its capacity is kept after removals, so the index's memory stays at its peak. Reclaiming
it is a separate item.

Measured (`docs/BENCHMARKS.md`, background build): the swap holds the lock for 19.6 to 22.6 ms. A build takes about 98
ms at 200,000 live documents. Searches during a build have p95 12.6 ms and p99 22.0 ms, against 74 and 79 ms for searches
during the blocking compaction. The peak heap rises to 154 MB against 74 MB before, because the old and the new row tables
are both in memory during a build.

Deviations and open items:

- **Deletes during a build stay dead in the swapped structure.** A delete made after the snapshot is applied to the new
  structure as a dead row. It is reclaimed by the next compaction, not by this one. Live counts are unaffected.
- **Compaction is re-checked when a build ends.** A delete that crosses the threshold during a build cannot start a
  compaction, because one is running. The build's end checks the threshold again and starts the next one. Before this
  check, the dead rows waited for a later delete.
- **The repeated-compaction test uses an explicit setup.** The fixture holds ids 0 to 9,999 and deletes nothing. The test
  deletes 0 to 5,999 first, so the live window it tracks is correct.
- **The longest write-lock hold is attributed.** It is the first index persist of a new database, in `create_collection`
  (80 ms; the next create takes 7 ms). The steady-state longest hold is the swap, at 25 ms. Section 15 and
  `docs/BENCHMARKS.md` give the per-operation figures.
- **Transient memory.** Old and new row tables coexist during a build. This is the cost measured above.
- **Power loss** is still not tested on hardware, and Windows rename behaviour is untested.

### Durability review (section 4 against the code)

Each failure path in `swap_locked` and `build_into`, and what a reopen finds:

- Build failure (any point): the temporary log is removed by `build_compaction`. The catalog was not touched, so the
  committed documents are unchanged.
- Failure before the rename, including a failed P1 catalog write: `undo_before_rename` reverts the catalog entry (its
  `Persist` outcome decides whether memory is reverted), removes the temporary log, and keeps the collection usable.
  A crash here leaves the pending record with the old log length, which the reopen reverts.
- Rename fails: the old handle is reattached, the catalog is reverted, the temporary log is removed. A failed reattach
  poisons.
- After the rename, a failure at "renamed", "directory synced", "swapped" or "pending cleared" poisons. The file on
  disk is the new log, and the pending record holds the new length, so a reopen completes the record.
- Directory sync: the directory fsync is done on Unix. On Windows `sync_parent` is a no-op, so the rename is not forced
  to disk there (see the platform section).
- Ordering: the tail is synced before P1, P1 before the rename, and the rename before P4. `compaction_transitions_run_in_the_documented_order`
  pins this order. Power loss at each step is not tested on hardware.

Found and fixed during this review: a failed swap restarted a build by itself. The post-build recheck ran after any
result, so while the threshold stayed crossed a failing swap started another build, and the test
`failed_swap_does_not_restart_a_compaction_by_itself` observed two builds within 200 ms. The recheck now runs only after
a successful swap. A failed compaction is retried by the next delete, which is an ordinary user operation.

### Scheduling of deletes made during a build

`deletes_during_a_build_that_make_it_due_are_compacted_without_another_write` runs a build, deletes 5,000 documents while
it runs (after the swap 3,000 live and 5,000 dead, which is due), and checks that the second compaction runs without any
further write: 3,000 rows in memory, the same as the live count. Removing the recheck makes it fail with 8,000 rows.

Deletes that stay below the threshold are not reclaimed until the threshold is crossed. That is the policy of
`should_compact` (more dead rows than live, and more than 4,096), not a defect: those rows cost memory, and no
background work is scheduled for them.

### Platforms

CI runs the Rust and Python tests on `windows-latest` (`.github/workflows/ci.yml`), but the workflow runs only on pushes to
`main` and on pull requests. This branch's R3 code has never run on Windows. What is known from the code:

- The swap releases the old log's handle before the rename, and reattaches it if the rename fails (Windows refuses to
  rename over an open file).
- `sync_parent` does nothing outside Unix, so the rename is not forced to disk on Windows. Power-loss durability of the
  swap there rests on the file system's own journaling, which is not tested.

Windows is therefore not verified for R3. Running it needs a trigger for this branch or a pull request; that is the
user's decision.

### Memory of the background build

See `docs/BENCHMARKS.md`, "Memory of background compaction". Summary: the transient is the new row table plus a
frame map of the whole log, and it is bounded and predictable at the sizes measured. A write-path spike unrelated to
compaction (writers and readers together) is larger than the compaction transient. It is present at commit a3c17ff,
before R3.
